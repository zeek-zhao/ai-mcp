---

## 1. 目的与适用范围

### 1.1 目的
参照 ISO 文档控制思路，保证项目文档：
- 有唯一编号与版本，可追溯；
- 存放位置固定、命名统一，不随意新建目录或散落文件；
- 每次更新、每个问题、每项任务都有书面记录；
- 历史记录只追加、不篡改，变更可回溯。

### 1.2 适用范围
仓库内所有 Markdown 文档、配置模板、AI 指令文档；代码文件不在本规范的编号范围内，但代码对应的设计说明必须落到对应文档。

---

## 2. 文档分层

| 层级 | 类别 | 存放目录 | 内容 | 示例 |
|---|---|---|---|---|
| L1 | 项目入口 | 仓库根目录 | 项目简介、导航、快速开始 | `README.md` |
| L2 | 规范文件 | `docs/` 根 | 文档与流程规则 | `docs/00-文档管理规范.md` |
| L3 | 工程文件 | `docs/<域>/` | 计划、架构、服务、安全、接入说明 | `docs/planning/项目计划书.md` |
| L4 | 记录文件 | `docs/operations/` | 任务、问题、变更日志、验收记录等过程留痕 | `docs/operations/任务清单.md` |
| L5 | AI 指令 | `ai/` | 给 AI 读取的上下文、提示词、交付规范 | `ai/实现提示词.md` |
| L6 | AI 技能 | `skills/` | AI 助手可直接加载的技能定义文件（SKILL.md） | `skills/ai-mcp-dev/SKILL.md` |

> L3 工程文件回答“是什么、为什么、怎么做”；L4 记录文件回答“做了什么、出了什么问题、状态如何”。两者不得混写在同一文件里。

## 3. 目录与命名规范

### 3.1 目录固定
- 工程文档只放入 `docs/` 下已定义的域目录；AI 指令文档只放入 `ai/`；AI 技能定义只放入 `skills/`（每个技能一个子目录，目录名即技能名）。
- 不得在仓库根目录、`docs/` 根目录随意新建未登记的文件夹。
- 确需新增目录时，先在本规范第 2 节补登层级与用途，再建目录。

### 3.2 文件命名
- 一律使用中文描述性名称，或英文 kebab-case；同一目录内保持一致，本仓库默认中文文件名。
- 文件名不含空格、日期、个人姓名、编号后缀（编号写进文档属性表，不写进文件名）。
- 配置模板统一为仓库根 `mcp.config.sample.json`（随附结构契约 `mcp.config.schema.json`）；真实本地配置 `mcp.config.json` 不带 `sample`，并被 `.gitignore` 排除；禁止在服务目录新建配置文件（ADR-007）。

### 3.3 域目录定义

| 目录 | 用途 |
|---|---|
| `docs/planning/` | 项目计划书、里程碑规划、范围与优先级 |
| `docs/architecture/` | 架构决策记录（ADR）、模块划分、技术选型理由 |
| `docs/services/` | 各 MCP 服务的选型、配置项、能力、版本兼容与限制 |
| `docs/security/` | 凭证管理、权限最小化、密钥扫描、审计要求 |
| `docs/host/` | 大模型 Host（Cursor / Claude Desktop 等）接入配置 |
| `docs/operations/` | 任务清单、问题记录、更新记录、验收记录等过程记录 |
| `ai/` | AI 指令与上下文，不存放工程实现说明 |
| `skills/` | AI 助手技能定义（SKILL.md）；每技能一个子目录，目录名即技能名（英文 kebab-case） |

### 4.1 编号结构
`DOC-<域>-<序号>`，AI 文档使用 `AI-<域>-<序号>`。

| 域前缀 | 含义 |
|---|---|
| SPEC | 规范文件 |
| REG | 台账/登记 |
| ARCH | 架构 |
| PLAN | 计划 |
| SVC | 服务 |

| OPS-TASK | 任务记录 |
| OPS-ISSUE | 问题记录 |
| OPS-CHANGE | 变更/更新记录 |
| OPS-ACCEPT | 验收记录（人工验收步骤与结论回填） |
| CTX | AI 上下文 |
| PROMPT | AI 提示词 |
| GOV | AI 交付规范 |
| SKILL | AI 技能定义 |

### 4.2 编号分配
- 编号在 `docs/01-文档台账.md` 中统一登记，一经分配不复用、不重排。
- 文档归档后编号保留，不分配给新文档。

## 5. 版本规则

### 5.1 版本号
采用语义化版本 `v<主版本>.<次版本>.<修订号>`：

| 变更类型 | 版本进位 | 说明 |
|---|---|---|
| 主版本 | 主版本 +1 | 方向性调整、架构决策变更、范围重大增减 |
| 次版本 | 次版本 +1 | 新增章节、新增服务/任务、功能补充 |
| 修订号 | 修订号 +1 | 文字修订、纠错、格式调整、错别字 |

### 5.2 版本与变更记录
- 每份文档头部属性表标注当前版本；末尾附「变更记录」表。
- 每次修改必须在变更记录中登记：版本、日期、变更人、变更摘要、原因/关联条目。
- 记录类文档（任务/问题/更新日志）自身的版本随主版本演进，但其条目按第 8 节追加管理。

## 6. 文档状态与流转

| 状态 | 标识 | 含义 | 可否作为实现依据 |
|---|---|---|---|
| 草稿 | D | 正在编写，内容可能调整 | 否 |
| 评审中 | R | 已提交待评审/核对 | 否 |
| 生效 | A | 已确认，可作为依据 | 是 |
| 归档 | X | 已被新文档取代或作废，仅留痕 | 否（引用须指向生效文档） |

流转：`D → R → A`；被取代时 `A → X`，并在台账中标注取代关系与替代文档编号。

状态语义约束：

- **生效（A）不得用于结论未回填的验收记录**（`DOC-OPS-ACCEPT-*`）：验收记录在步骤就绪、结论栏为空时状态为 `R`，结论由负责人全部回填后才转为 `A`。
- **评审中（R）的适用场景**：已提交、待评审或核对的规范与设计文档；步骤已就绪但结论尚未由负责人完成的验收记录。`R` 状态文档不得作为实现或验收依据。
- 以上两条由台账审计（`scripts/lib/ledger-audit.ps1`，CI 与合并前自检共用）校验：状态为 `A` 的验收记录结论栏全空即失败。

## 8. 记录类文档规则（L4）

### 8.1 只追加、不改写历史
- 任务、问题、更新记录以**条目**形式追加；已关闭条目的历史描述不得删除。
- 状态更新直接在条目内更新状态字段，并在“更新记录”或条目备注中留痕；不删除旧状态。

### 8.2 任务清单（DOC-OPS-TASK-001）
每条任务字段：任务编号、关联里程碑、任务名称、描述、依赖、验收标准、负责人、状态、创建/更新日期、关联 Issue/PR。
状态枚举：待开始 / 进行中 / 待验收 / 已完成 / 已阻塞 / 已取消。
任务状态口径：「已完成」只用于「交付物已形成且验收通过」的任务——验收通过指负责人已确认，或交付物带有 CI 强制校验且持续通过（如模板与 Schema 校验、旧配置引用检查、台账审计）；纯文档产出在负责人确认前记「待验收」，并在验收标准末尾备注交付物形态。按本口径调整状态时只改状态与更新日期，不改写条目的其他内容。

### 8.3 问题记录（DOC-OPS-ISSUE-001）
每条问题字段：问题编号、发现日期、来源（开发/评审/CI/用户反馈）、现象、原因分析、影响范围、应对措施、优先级、状态、关联版本/Issue/PR。
状态枚举：开放 / 处理中 / 已解决 / 已规避 / 已关闭。

### 8.4 更新记录（DOC-OPS-CHANGE-001）
按版本倒序登记；每条字段：版本/日期、变更类型、变更摘要、涉及文档/模块、关联 PR、负责人。
变更类型：新增 / 变更 / 修复 / 文档 / 重构 / 杂项。

### 8.5 验收记录（DOC-OPS-ACCEPT-<序号>）
用于需要由负责人在本机人工执行的验收：每个验收对象（服务或场景）一节，包含前置条件、操作步骤、期望输出、失败排查表与结论栏。
- 期望输出（工具数、清单要点、提示文案）须来自实际运行结果，不得凭印象填写。
- 结论栏由执行人回填：结果（通过 / 不通过 / 未执行）、执行人、日期、备注。**AI 与文档编写者不得预填结论**，默认留空。
- 执行人回填结论后，在变更记录登记版本与关联任务；未执行的验收项写「未执行」，不得留白当作通过。
- **结论栏的位置与识别规则**：结论栏表格放在标题含「结论」的小节下，表头列名以「结果」或「结论」开头；台账审计据此判断结论是否回填（其他表格，如握手探活的「结果 / 输出 / 说明」对照表，不计入结论栏）。
- **状态流转**：步骤就绪时状态为 `R`；结论全部回填后转 `A` 并同步台账（见第 6 节状态语义约束）。
- **AI 执行记录的写法**：AI 用真实凭证做只读验证的留痕，放在各服务结论栏之后的「执行记录」小节，写明时间、执行人、方式与现象，不含凭证值、内部地址与账号值；小节标题不得含「结论」，表格列名不得以「结果」或「结论」开头，以免被台账审计计为已回填；执行记录不替代结论栏。

## 9. 新增与变更文档流程

1. **新增**：在台账中申请编号 → 按目录规范落位 → 补属性表与变更记录 → PR 中关联任务/问题条目。
2. **变更**：修改版本号与属性表“最后更新” → 在文末变更记录追加一行 → 同步更新台账中的版本与状态。
3. **迁移/重命名**：先在台账登记旧编号与新路径；旧条目标注归档与替代关系。
4. **作废**：状态置为 X，正文保留并在顶部注明“已作废，见 <替代文档编号>”。

## 10. 评审检查项

PR 涉及文档时，检查：
- [ ] 文档已在台账登记，编号唯一且未复用；
- [ ] 目录、命名符合本规范；
- [ ] 属性表字段完整，版本/状态正确；
- [ ] 变更记录已追加；
- [ ] 无真实凭证、内部敏感地址写入；
- [ ] 记录类条目状态与实际一致，历史未被删改；
- [ ] 台账审计通过（`scripts/lib/ledger-audit.ps1`，CI 与合并前自检同款）：台账与文内编号 / 版本 / 状态 / 最后更新一致；结论未回填的验收记录未标 `生效（A）`。
