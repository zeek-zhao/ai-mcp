## 1. 总体架构

```
┌──────────────────────────── Host（Cursor / Claude Desktop）────────────────────────────┐
│  多个 MCP Client（一对一连接各自 Server）                                                │
└───────┬──────────────┬──────────────┬──────────────┬──────────────┬──────────────────┘
        │ stdio        │ stdio        │ stdio        │ stdio
┌───────▼──────┐ ┌─────▼───────┐ ┌──▼─────────┐ ┌──▼───────────┐
│ mcp-gerrit   │ │ mcp-github  │ │ mcp-jenkins│ │ mcp-atlassian│
│ (独立进程)    │ │ (独立进程)   │ │ (独立进程)  │ │ (独立进程)    │
└───────┬──────┘ └─────┬───────┘ └──┬─────────┘ └──┬───────────┘
        │ REST/API      │ REST/API    │ REST/API     │ REST/API
┌───────▼──────┐ ┌─────▼───────┐ ┌──▼─────────┐ ┌──▼───────────┐
│ Gerrit       │ │ GitHub/GHES │ │ Jenkins    │ │ Jira+Confluence│

本地总控：scripts/mcpctl.ps1（注册表 + 统一配置 mcp.config.json + 配置向导 + 诊断/探活/遗留清理 + Host 配置导出 + Bootstrap；服务本体由 Host 按需 stdio 拉起，各启动器经 MCP_SUITE_CONFIG 读取统一配置）
```

## 2. 架构决策记录

### ADR-001 采用多独立 MCP Server，而非单聚合服务
- **状态**：已接受
- **背景**：四个对接系统模型差异大（评审、代码托管、CI、工单/文档），工具命名与鉴权各不相同。
- **决策**：一服务一独立进程，由 Host 分别连接。
- **理由**：故障隔离、独立鉴权与日志、可单独调试启停；符合 MCP 原生设计；避免工具名冲突与依赖膨胀。
- **取舍**：Host 需配置多条连接；进程数多于单聚合方案，但可接受。

### ADR-002 总控使用 PowerShell 菜单脚本
- **状态**：已接受
- **决策**：总控以 PowerShell 实现全中文交互菜单。
- **理由**：Windows 自带，无需额外全局运行时；原生支持进程/PID/计划任务管理。
- **约束**：路径全部相对仓库定位；需在文档注明所需执行策略。

### ADR-003 Jenkins 零侵入接入
- **状态**：已接受
- **决策**：不安装 Jenkins 插件，由独立本地 MCP 进程通过 REST API + API Token 调用。
- **理由**：满足“不改 Jenkins 实例”的硬性约束；权限复用 Jenkins 账号体系。

### ADR-004 依赖仓库内隔离
- **状态**：已接受
- **决策**：各子服务在自身目录内维护虚拟环境/依赖目录与锁定文件，不使用系统全局环境作为运行前提。
- **理由**：可复现、不污染全局、便于新机器 Bootstrap 重建。

### ADR-005 常驻使用任务计划程序
- **状态**：已取消（2026-11-25，随 ADR-006 传输模型调整取消；原“登录常驻”重定义为登录预检与环境自愈，见 M9）
- **决策（原）**：登录自动启动通过 Windows 任务计划程序实现，默认关闭。
- **取消原因**：模型一下服务由 Host 按需 stdio 拉起，登录常驻会与 Host 生命周期冲突（ADR-006）。


### ADR-006 stdio 服务由 Host 拉起，mcpctl 仅做配置与环境治理
- **状态**：已接受（2026-11-25，传输模型整改，问题编号 DEV-003/DEV-004）
- **背景**：M3 骨架曾按“mcpctl 后台托管服务”设想实现——以独立进程拉起服务、把服务 stdout/stderr 重定向到日志文件、写 PID 文件托管、以 taskkill（不带 /F）做“通知退出”。核查发现该模型与 MCP stdio 传输本质冲突：stdio 通道必须由 MCP Client（Host）与服务进程一对一持有；被 mcpctl 托管的进程其 stdout 已被重定向、stdin 未连接，Host 无法与之通信；且 Windows 下 taskkill 不带 /F 对无窗口控制台进程无效，停止流程实为必然超时后强杀（DEV-004）。
- **决策**：采用【模型一】——MCP 服务由 Host（Cursor / Claude Desktop 等）按需以 stdio 拉起，生命周期由 Host 管理；mcpctl 收缩为治理工具：服务注册表、配置向导、依赖环境 Bootstrap、启动命令诊断、MCP 握手探活、遗留进程识别与清理（二次确认强杀）、Host 配置片段导出。
- **理由**：①stdio 传输要求 Client 与 Server 一对一持有标准流，任何中间托管都会破坏通道；②按需拉起无闲置进程、无端口暴露；③治理工具与运行时解耦，服务接入（M5–M8）只需在注册表回填启动命令并在 Host 配置中引用，无需改造 mcpctl。
- **被否方案**：
  - **方案二（后台托管 + Host HTTP/SSE）**：服务改为常驻 HTTP/SSE、mcpctl 保留托管。否决理由：需要为每个服务增加 HTTP 服务化改造与端口管理，破坏“stdio 本地按需拉起”的既定约束；常驻进程带来闲置资源占用与额外的安全暴露面；与 Host 生态主流的 stdio 接入方式脱节。
  - **方案三（保留 mcpctl 托管 + 停止流程改良）**：仅修复 taskkill 问题。否决理由：不解决根因——被托管进程的 stdio 已被重定向，Host 无论如何都无法通信；DEV-003 的冲突依旧存在。
- **影响面**：service-utils.ps1 重写为诊断/探活/遗留清理（删除托管启动与伪停止流程）；mcpctl.ps1 菜单重构；M3 验收标准改写；M9“登录常驻”取消并重定义为登录预检与环境自愈；M10 的 Host 配置导出提前具备；Host 接入配置文档升级为可用模板。

### ADR-007 配置集中：单一统一配置文件 mcp.config.json
- **状态**：已接受（2026-11-26，统一配置改造）
- **背景**：M5–M8 接入后，四个服务各有一份配置模板与本地配置（`mcp-*/` 目录下的 JSON 与 `.env`），字段命名各异；配置向导按服务逐份复制模板，注册表要为每个服务维护模板路径与本地配置路径，四个启动器各自解析不同格式。新增一个字段（如 Atlassian 部署类型）需要在模板、向导、启动器、文档多处同步，容易漂移。
- **决策**：四个服务的运行配置集中到仓库根**单一文件** `mcp.config.json`（已 gitignore），按 `services.<key>` 分段。仓库只保留 `mcp.config.sample.json`（参考值 + `_hints` 中文提示）与 `mcp.config.schema.json`（JSON Schema，结构契约）；字段说明以 `docs/services/配置字段说明.md` 为权威表。依赖清单（`requirements.txt`、`package.json` / `package-lock.json`）仍留在各服务目录，只合并“配置”。注册表以 `ConfigKey` 指向配置段；读取、原子写入、就绪判定统一由 `scripts/lib/suite-config.ps1` 提供；启动器通过环境变量 `MCP_SUITE_CONFIG`（未设置时回退 `<服务目录>/../mcp.config.json`）读取本服务配置段，Gerrit 启动器在运行期把本段合成为上游要求的嵌套配置临时文件（`var/tmp/`），退出时删除。
- **理由**：①一份文件即一份事实，录入、就绪判定、诊断、导出、启动器共用同一读取模块；②字段提示与参考值进模板，向导不必重复维护字段目录；③Schema 让必填集合成为可在 CI 中校验的契约；④新增服务只需在注册表登记 `ConfigKey`，并在 sample / Schema 中增加一段。
- **被否方案**：
  - **保留分服务配置文件**：否决理由：字段分散、多处同步、易漂移；向导与注册表需维护每个服务的模板与本地路径。
  - **纯环境变量注入（不落盘）**：否决理由：Host 配置只适合传少量非敏感变量，把凭证写进 Host 配置违反“凭证不进 Host 配置”的既有约束，也无法提供带参考值与中文提示的录入体验。
- **影响面**：影响半径变大——单文件聚合四个服务的全部凭证，泄露影响全部服务。缓解措施：①写入走同目录临时文件 + 原子替换，失败不产生半截文件，覆盖已有配置前先提示；②文件仅限本机当前用户可读（沿用仓库目录的文件系统权限，脚本不额外放宽）；③不自动生成带凭证的备份副本，确需备份时手工复制到同等受控位置并同等保管；④禁止放入网盘、邮件等同步或共享渠道（见 `docs/security/安全与凭证管理.md`）；⑤`enabled=false` 可整段停用某服务；⑥CI 校验模板与 Schema，真实配置一旦被跟踪即失败。模块影响：新增 `scripts/lib/suite-config.ps1`；注册表改用 `ConfigKey`；配置向导改为单文件逐字段录入并支持从旧配置导入；四个启动器统一读取；Host 配置导出携带 `env.MCP_SUITE_CONFIG` 并跳过已禁用服务；分服务配置模板下线。

### ADR-008 Magpie 网关作为可选的中间层（默认仍为 Host 直连）
- **状态**：已接受（2026-11-26，Magpie 网关接入，TASK-PROXY-01）
- **背景**：多个 agent / 客户端都要使用这四个服务时，直连模式需要在每个 Host 里重复登记四条启动命令；给外部客户端发放受限的只读访问也需要统一的授权点。本机的 Magpie（Windows 原生 MCP 网关）可以用命令模式登记同一组启动命令、统一拉起进程，并按网关密钥向客户端授权。
- **决策**：把网关定位为**可选层**，默认接入方式不变（Host 直连，ADR-006）。仓库只提供不含凭证的样例 `gateway.routes.sample.json`（`<仓库根>` 为占位符；四条 `command` / `args` 与注册表 `StartCommand` 一致，由 CI 校验；样例不得出现凭证类字样与本机绝对路径）与 `docs/host/Host接入配置.md` 第 4 节的说明；真实路由只存在于本机 Magpie 配置，不入库。四个启动器与 `mcp.config.json` 结构不变，凭证仍只在本机 `mcp.config.json`，网关路由只传 `env.MCP_SUITE_CONFIG`。
- **与 ADR-006 的关系（例外）**：网关模式下进程生命周期由 Magpie 管理。实测：客户端接入网关与检索工具不启动服务；服务在**第一次被调用时**才拉起（按服务各自启动）；会话结束后进程不立即退出，Magpie 复用它们，**空闲约 10 分钟后回收**。这是 ADR-006「按需拉起、会话结束即退出」在回收时机上的例外——选用网关即接受「会话结束后约 10 分钟内仍有服务进程在运行」；统一配置修改后需等 Magpie 回收或重启 Magpie 后才生效。
- **理由**：①不改启动器与统一配置，网关只是又一个 Host；②样例与注册表由 CI 绑定，启动命令变更时不会漂移；③客户端授权集中在网关，写工具一律不下放；④可随时回退直连（`magpie library mcp off <服务名>`，或改用菜单 6 导出的配置）。
- **被否方案**：
  - **把网关做成默认接入方式**：否决理由：网关模式下服务在会话结束后延迟回收（约 10 分钟），与 ADR-006「会话结束即退出」有出入，且让所有使用者依赖网关。
  - **把真实路由（含本机路径）入库**：否决理由：路由含本机绝对路径，属本机信息；一旦有人把凭证写进 env 就会随之路入库。
- **影响面**：新增 `gateway.routes.sample.json`、`.gitignore` 规则 `gateway.routes.json`、CI「网关路由样例校验」；`docs/host/Host接入配置.md` 新增「Magpie 网关模式（可选）」；mcpctl 菜单行为、四个启动器、统一配置结构均不变；直连文档与两份验收记录不受影响。

## 3. 模块职责

| 模块 | 职责 | 不负责 |
|---|---|---|
| `scripts/mcpctl.ps1` | 主菜单入口，调度各 lib 能力 | 直接实现外部系统调用 |
| `scripts/mcpctl.config.ps1` | 服务注册表（含 `ConfigKey`）、全局参数 | 业务逻辑 |
| `scripts/lib/suite-config.ps1` | 统一配置 `mcp.config.json` 的读取、原子写入、就绪判定、模板初始化、字段提示读取（ADR-007） | 启动服务、调用外部系统 |
| `scripts/lib/service-utils.ps1` | 启动命令诊断、MCP 握手探活、遗留进程识别与清理、状态表格 | 托管服务进程（由 Host 拉起，见 ADR-006）、配置录入 |
| `scripts/lib/config-wizard.ps1` | 统一配置逐字段录入（展示参考值与中文提示）、从旧配置导入、就绪判断、连通性测试入口 | 进程管理 |
| `scripts/lib/log-utils.ps1` | 日志与审计（脱敏） | 业务判断 |
| `scripts/bootstrap.ps1` | 依赖环境初始化 | 服务运行 |
| `scripts/autostart.ps1` | 登录预检：检查运行时（Python / Node.js / npm / curl）、依赖环境、统一配置就绪状态、启动命令，输出中文汇总与可直接执行的修复命令，结果保存到 `logs\preflight-last.json`；环境自愈：显式允许（逐次确认或全局参数 `PreflightAutoBootstrap`）后调用 Bootstrap 初始化缺失环境（M9 重定义；原常驻已取消） | 拉起或托管 MCP 进程（见 ADR-006）；创建计划任务（登录触发默认关闭，由用户自行配置）；修改统一配置；下载二进制 |
| `scripts/lib/ledger-audit.ps1` | 文档台账一致性审计：台账 ↔ 文内属性表（编号 / 版本 / 状态 / 最后更新）、变更记录末行、磁盘 Markdown 是否已登记；验收记录状态语义校验（结论未回填不得为生效（A））；CI 与合并前自检共用 | 修改文档；业务逻辑 |
| `scripts/lib/gateway-routes.ps1` | Magpie 网关路由生成（唯一实现，ADR-008）：从注册表 StartCommand 拼出四条路由（服务名固定，`env` 只放 `MCP_SUITE_CONFIG`）；写入前自检（与注册表逐项一致、不含凭证类字样）并输出登记命令；mcpctl 菜单 8 与 CI 自检共用 | 登记 Magpie 条目（由负责人在终端或界面执行）；保存任何凭证；替代 Host 直连（网关是可选层） |
| `scripts/new-mcp.ps1` | 新增服务脚手架：按 Id / 显示名 / 技术栈生成服务目录骨架（带统一配置校验与模板值拒启的启动器模板、依赖清单、README），并打印剩余需手工完成的 6 处修改 | 替代手工完成第 4–9 步；把凭证或本机路径写进生成文件 |
| `scripts/tests/` | 四服务自检（直连 / 结构 / 网关三种模式，四态退出码）；结构模式进 CI，新增服务须补对应用例 | 托管服务进程；验证写操作 |
| `mcp-*` 子服务 | 启动器（读取统一配置并拉起上游）+ 对接对应外部系统的 MCP 能力（由 Host 按需 stdio 拉起） | 跨服务编排；在服务目录保存配置（配置只存在于仓库根 `mcp.config.json`） |
